# Business Rules for Energo

## 1. Introduction

Energo is an energy management system that allows users to manage their energy consumption through prepaid meters. The system supports three roles: Regular User, Admin, and Auditor. This document defines the business rules that govern the system's behavior.

## 2. Core Business Entities

### 2.1 User
- **Attributes**: id, username, email, password_hash, role_id, status_id, created_at, last_login
- **Roles**: 
  - `user` - Regular user with basic functionality
  - `admin` - Administrator with full user management and pricing control
  - `audit` - Auditor for monitoring and compliance
- **Statuses**:
  - `Activo` - Active account, full access
  - `Pausa` - Temporarily paused, cannot recharge
  - `Deshabilitado` - Permanently disabled
  - `Suspendido` - Suspended by admin

### 2.2 Energy Card (Meter)
- **Attributes**: id, user_id, card_number, name, current_balance, current_kwh, last_recharge, released, released_by_user_id, released_at
- **Rules**:
  - Each card has a unique card_number
  - A card can be linked to at most one user at a time
  - Cards can be "released" (unlinked) and become available for claiming
  - Balance is stored in COP (Colombian Pesos)
  - Energy amount is stored in kWh

### 2.3 Recharge Pin
- **Attributes**: id, user_id, card_number, pin_code, amount, kwh, kwh_price_at_time, created_at
- **Rules**:
  - Generated when a user recharges
  - PIN encodes transaction details using STS-20 algorithm
  - Stores the kWh price at time of recharge for historical accuracy
  - PIN is used as proof of recharge

### 2.4 Employee Code
- **Attributes**: id, code, role_id, used, employee_usage_id, created_at, used_at
- **Rules**:
  - One-time use codes for creating admin or auditor accounts
  - Generated by auditors
  - Format: ROLE-XXXXXXXX (e.g., ADMIN-ABC12345)
  - Cannot be reused once marked as used

### 2.5 User Profile
- **Attributes**: user_id, primer_nombre, segundo_nombre, primer_apellido, segundo_apellido, tipo_identificacion, numero_identificacion, direccion, telefono
- **Rules**:
  - One-to-one relationship with user
  - Document type and number must be unique across all users
  - Phone number must be unique
  - Required fields: primer_nombre, primer_apellido, tipo_identificacion, numero_identificacion

### 2.6 kWh Price
- **Storage**: In `settings` table with key='kwh_price' and in `kwh_price_history` for audit
- **Rules**:
  - Only admins can update the price
  - All changes are logged with admin user ID and timestamp
  - Current price is stored in settings, history is preserved

## 3. Authentication & Authorization Rules

### 3.1 Authentication
- Users authenticate with username and password
- Passwords are hashed using bcrypt with cost factor 10
- Failed login attempts are logged but not rate-limited (future enhancement)
- Session is established via express-session with server-side storage
- Session cookie is httpOnly and sameSite=lax
- In production, cookie must be secure (HTTPS only)

### 3.2 Authorization (RBAC)
- **Regular User**:
  - Can manage own account (profile, password, status)
  - Can manage own energy cards (add, rename, release)
  - Can recharge own cards (by amount, by kWh, or by PIN)
  - Can view own recharge history
  - Cannot access admin or audit endpoints

- **Admin**:
  - All regular user permissions
  - Can view all users
  - Can update user email
  - Can change user status (Activo, Pausa, Deshabilitado, Suspendido)
  - Can suspend/unsuspend users
  - Can send password reset links (mock implementation)
  - Can link/release meters to/from any user
  - Can update kWh price
  - Can view all recharge history (not just own)
  - Cannot access audit-specific endpoints

- **Auditor**:
  - Cannot perform regular user operations
  - Can view all admins
  - Can view all employees (admins + auditors)
  - Can generate employee codes for admin/auditor roles
  - Can view all employee codes (used/unused)
  - Can view sales metrics (totals and daily breakdown)
  - Can view kWh price history
  - Can view all security logs
  - Can view security logs by user

### 3.3 Session Validation
- Every authenticated request revalidates user status
- Users with status `Deshabilitado` or `Suspendido` are denied access
- Session is destroyed on logout

## 4. User Registration Rules

### 4.1 Regular User Registration
- Required fields: username, password, email, card_number (serial of energy card)
- Username must be unique (case-insensitive)
- Email must be unique (case-insensitive)
- Password must meet policy requirements (see Section 5)
- Card number:
  - Must be 11+ digits
  - Must not already be linked to another active user
  - If card exists but is released (unlinked), it will be claimed and linked to new user
- On success:
  - User is created with role_id=3 (user) and status_id=1 (Activo)
  - Energy card is created and linked
  - User is automatically logged in (session established)

### 4.2 Employee Registration (Admin/Auditor)
- Requires valid, unused employee code
- Employee code determines the role (admin or audit)
- Card number is NOT required for employee registration
- Employee code is marked as used and linked to the created user
- Employee code can only be used once

## 5. Password Policy

### 5.1 Requirements
- Minimum length: 12 characters
- Must contain at least 3 of the following 4 character classes:
  - Lowercase letters (a-z)
  - Uppercase letters (A-Z)
  - Digits (0-9)
  - Symbols (non-alphanumeric)
- Must not contain whitespace
- Must not contain the username (case-insensitive)
- Must not contain the local part of the email (before @)

### 5.2 Storage
- Passwords are hashed using bcrypt
- Cost factor: 10 (configurable, currently hardcoded)
- Never stored in plain text

### 5.3 Change Password
- Users must provide current password to change
- New password must meet policy requirements
- Password change updates `password_changed_at` timestamp

### 5.4 Password Reset
- Token-based reset flow (currently mock implementation)
- Token is SHA-256 hashed before storage
- Token expires after 1 hour
- Single-use: token is marked as used after successful reset
- Token validation checks: exists, not used, not expired

## 6. Energy Card Management Rules

### 6.1 Card Creation
- Regular users: card created automatically during registration with provided serial
- Admins can link existing unlinked cards to users
- Card numbers must be unique across the system

### 6.2 Card States
- **Active**: linked to a user (user_id is not NULL, released=0)
- **Released**: unlinked from user (user_id is NULL, released=1, released_by_user_id and released_at set)
- Released cards can be claimed by new users

### 6.3 Card Operations
- **Rename**: Users can update the display name of their own cards
- **Release**: Users can unlink their own cards; admins can release cards from any user
- **Claim**: New users can claim a released card by providing its serial during registration
- **Transfer**: Admins can transfer card ownership between users

### 6.4 Card Balance
- Balance stored in two forms:
  - `current_balance` - monetary value in COP
  - `current_kwh` - energy amount in kWh
- Both are updated atomically during recharge
- `last_recharge` timestamp updated on each recharge

## 7. Recharge Rules

### 7.1 Recharge Methods
Users can recharge in three ways:

1. **By Amount (COP)**:
   - User enters amount in Colombian Pesos
   - System calculates equivalent kWh using current price
   - PIN generated with both values

2. **By Energy (kWh)**:
   - User enters desired energy in kWh
   - System calculates required amount using current price
   - PIN generated with both values

3. **By PIN Code**:
   - User enters a pre-generated PIN code (from physical card or other source)
   - System validates PIN exists and belongs to user
   - Balance updated with the amount and kWh encoded in PIN

### 7.2 Recharge Constraints
- Users cannot recharge if account status is `Pausa`, `Deshabilitado`, or `Suspendido`
- Recharge amount must be positive
- Calculated kWh is rounded to 2 decimal places
- PIN generation uses STS-20 algorithm with:
  - Card-specific derived key
  - Amount in cents
  - Days since STS epoch (1993-01-01)
  - Random nonce
  - HMAC-SHA256 for integrity
  - Luhn check digit for validation

### 7.3 Transaction Recording
- Every recharge creates a record in `recharge_pins` table
- Record includes: user_id, card_number, pin_code, amount, kwh, kwh_price_at_time, created_at
- `kwh_price_at_time` captures the price used for conversion
- PIN code format: 19-digit body + 1 check digit (20 digits total)

### 7.4 PIN Validation
- PIN includes Luhn check digit for basic validation
- PIN can be verified by decoding and checking HMAC
- PINs are single-use (consumed upon redemption)

## 8. Pricing Rules

### 8.1 kWh Price
- Current price stored in `settings` table with key='kwh_price'
- Price is a decimal value representing COP per kWh
- Only admins can modify the price
- Price changes are logged in `kwh_price_history` with:
  - admin_user_id
  - price_cop
  - created_at timestamp

### 8.2 Price Usage
- Current price is used for real-time COP↔kWh conversion during recharge
- Historical recharges display the price that was in effect at the time
- Dashboard shows current price to all users

## 9. Security & Audit Rules

### 9.1 Security Logging
All significant events are logged to `security_logs`:
- User registration (success/failure)
- Login (success/failure)
- Logout
- Password reset requests
- Password changes
- Recharge operations
- Admin actions (user status changes, email updates, price changes)
- Employee code generation
- JSON parsing errors
- Authorization failures

Each log entry includes:
- event_type
- username (if applicable)
- event_time
- ip_address
- details (JSON-serializable additional context)

### 9.2 IP Address Tracking
- Client IP is captured from request headers (X-Forwarded-For or connection.remoteAddress)
- Used for security analysis and forensic investigation

### 9.3 Data Integrity
- Database transactions used for multi-step operations
- Row-level locking (SELECT ... FOR UPDATE) for:
  - Employee code validation and marking
  - Energy card balance updates
- Duplicate entry errors handled gracefully (e.g., race condition on card creation)

### 9.4 SQL Injection Prevention
- All database queries use parameterized statements
- No string concatenation for query values
- Stored procedures also use parameters

## 10. User Profile Rules

### 10.1 Profile Completion
- Users are required to complete their personal data after registration
- Required fields: primer_nombre, primer_apellido, tipo_identificacion, numero_identificacion
- Completion status tracked in `user_flags.personal_data_filled`
- `filled_at` timestamp set when profile is first completed
- Incomplete profiles trigger a prompt in the UI (for regular users only)

### 10.2 Profile Updates
- Users can update their profile at any time
- Document changes (tipo_identificacion or numero_identificacion):
  - Are logged in `user_document_changes` table
  - Can only be changed once (enforced by unique constraint on user_id in user_document_changes)
  - Require special handling/approval (business rule: one-time change only)

### 10.3 Uniqueness Constraints
- `numero_identificacion` must be unique across all users (with tipo_identificacion)
- `telefono` must be unique across all users
- These constraints are enforced at database level with unique indexes

## 11. Account Status Transitions

### 11.1 Allowed Statuses
- **Activo** → **Pausa**: User self-service or admin action
- **Activo** → **Deshabilitado**: Admin action (permanent)
- **Activo** → **Suspendido**: Admin action (temporary)
- **Pausa** → **Activo**: User self-service (reactivation) or admin action
- **Suspendido** → **Activo**: Admin action (unsuspend)
- **Deshabilitado**: Permanent, cannot be reversed (business rule)

### 11.2 Status Impact on Operations
- **Pausa/Deshabilitado/Suspendido**: Cannot recharge
- **Deshabilitado/Suspendido**: Cannot login (blocked at authentication)
- **Pausa**: Can login but recharge is blocked
- **Activo**: Full access

### 11.3 Reactivation Flow (Pausa)
- Users in `Pausa` can reactivate through a dedicated reactivation page
- Requires password confirmation
- Sets status back to `Activo`

## 12. Admin Operations Rules

### 12.1 User Management
- Admins can view all users in a paginated list
- Admins can view detailed user information including:
  - Profile data
  - Linked energy cards with balances
  - Activity logs (security logs filtered by username)
- Admins can update user email (must be unique)
- Admins can change user status to any valid status
- Admins can suspend/unsuspend users
- Admins can send password reset emails (mock - token returned in response)

### 12.2 Meter Management
- Admins can link any unlinked energy card to any user
- Admins can remove (release) meters from users
- When releasing, admin's user_id is recorded as `released_by_user_id`

### 12.3 Pricing
- Only admins can update the kWh price
- Price change is immediately effective
- Historical price is preserved for existing recharge records
- Price change is logged with admin's user ID

### 12.4 Visibility
- Admins see all users' recharge history (not just their own)
- Admins see user email in recharge history table
- Admins see user ID in recharge history table

## 13. Auditor Operations Rules

### 13.1 Employee Management
- Auditors can generate one-time employee codes for:
  - `admin` role
  - `audit` role
- Codes are 8-character random strings with role prefix (e.g., ADMIN-XYZ123)
- Characters exclude ambiguous ones (no I, O, 0, etc.)
- Codes are automatically marked as used when someone registers with them
- Auditors can view all generated codes with usage status

### 13.2 Metrics & Reporting
- Auditors can view sales metrics:
  - Total codes sold (recharges) in a period
  - Total amount (COP) in period
  - Total kWh sold in period
  - Daily breakdown for the last N days (default 30)
- Metrics are calculated from `recharge_pins` table
- All amounts and kWh are summed

### 13.3 Security Monitoring
- Auditors can view all security logs (all users)
- Can filter logs by specific user
- Logs include: event type, username, timestamp, IP, details
- Limited to most recent 200 entries by default

### 13.4 Price History
- Auditors can view complete history of kWh price changes
- Each entry shows: admin who changed it, new price, timestamp

## 14. State Transition Rules

### 14.1 User Lifecycle
1. **Registration** → Status: Activo, Role: user (or admin/audit with employee code)
2. **Active** → Can perform all normal operations
3. **Paused** → Can login but cannot recharge; can reactivate
4. **Suspended** → Cannot login; admin must unsuspend
5. **Disabled** → Cannot login; permanent

### 14.2 Energy Card Lifecycle
1. **Created** → Linked to user, released=0
2. **Released** → Unlinked from user, released=1, released_by_user_id set
3. **Claimed** → Released card linked to new user, released=0, released_by_user_id cleared

### 14.3 Employee Code Lifecycle
1. **Generated** → used=0, available
2. **Used** → used=1, used_at set, employee_usage_id linked to user

## 15. Validation Rules

### 15.1 Input Validation
- Username: required, unique, min 3 characters (implied)
- Email: required, valid format, unique
- Password: meets policy (Section 5)
- Card number: required for regular users, 11+ digits, numeric only
- Amount/kWh: positive numbers, finite, within database precision limits
- PIN code: required for PIN recharge, must exist and belong to user

### 15.2 Business Validation
- Cannot create user with existing username or email
- Cannot create energy card with existing card_number
- Cannot recharge if account is not Activo
- Cannot recharge if card does not belong to user
- Cannot use expired or already-used PIN
- Cannot generate employee code for invalid role
- Cannot update kWh price to non-positive value

## 16. Error Handling Rules

### 16.1 User-Facing Errors
- Validation errors return 400 with descriptive message
- Authentication failures return 401
- Authorization failures return 403
- Resource not found returns 404
- Server errors return 500 with generic message (details logged)

### 16.2 Security Error Responses
- Invalid credentials: generic "Invalid credentials" (no hint which field was wrong)
- Account status blocked: specific message indicating status
- Duplicate registration: "Username already exists" or "Email already exists"

### 16.3 Transaction Rollback
- On any error during multi-step operations, database transaction is rolled back
- Partial updates are prevented
- Consistent state maintained

## 17. Data Retention & History

### 17.1 Historical Data
- `kwh_price_history`: All price changes retained indefinitely
- `recharge_pins`: All recharge records retained indefinitely
- `security_logs`: Logs retained until manual cleanup (no automatic pruning)
- `user_document_changes`: Document change history retained indefinitely
- `password_resets`: Tokens expire after 1 hour, but records remain

### 17.2 Audit Trail
- All critical operations create immutable records
- `created_at` and `updated_at` timestamps on most tables
- `password_changed_at` on users
- `last_login` on users
- `released_at` on energy cards
- `used_at` on employee codes and password resets

## 18. Integration & API Rules

### 18.1 API Base Path
- All API endpoints are prefixed with `/api/`
- Authentication uses session cookies (not tokens)
- CORS configured to allow credentials from configured client origin

### 18.2 Endpoint Grouping
- `/api/auth/*` - Authentication (login, register, logout, password reset)
- `/api/user/*` - User operations (profile, password change, status)
- `/api/admin/*` - Admin operations (user management, pricing)
- `/api/audit/*` - Auditor operations (metrics, logs, employee codes)
- `/api/meters/*` - Energy card management
- `/api/recharge/*` - Recharge operations

### 18.3 Response Format
- Success: `{ message: string, ...additional data }`
- Error: `{ error: string }` with appropriate HTTP status
- Data endpoints return JSON objects with relevant data

## 19. Frontend Business Rules

### 19.1 Navigation & Access Control
- Unauthenticated users see only Home, Login, Register
- Authenticated regular users see Dashboard, Profile, Security, Logout
- Admins see additional "Users" menu item
- Auditors see additional "Employee Registration" menu item
- UI adapts theme color based on role (green for user/admin, black for audit)

### 19.2 Dashboard Behavior
- Regular users see:
  - Their own cards
  - Their own recharge history
  - Current balance and kWh
  - Recharge form
- Admins see:
  - All of regular user's info
  - All users' recharge history
  - Admin controls (price update, user management links)
  - kWh price history in movements table
- Auditors see:
  - All of admin's info
  - Sales metrics (totals and daily)
  - Security logs
  - kWh price history

### 19.3 Profile Completion Flow
- Regular users must complete personal data before full access
- Incomplete profile shows modal prompt
- Prompt offers to open profile page in new tab
- System polls for completion every 3 seconds
- Upon completion, auto-redirects to dashboard after 2 seconds

### 19.4 Recharge Form
- Three modes: COP, kWh, PIN
- Radio buttons to switch modes
- Input validation on client (mirrors server policy)
- Disabled if account is Pausa
- Shows equivalent value in other mode (e.g., entering COP shows calculated kWh)
- On success, displays generated PIN prominently
- Optimistically updates balance display

### 19.5 Meter Selection
- Users with multiple cards can switch between them
- Selected card determines which card is recharged
- Card selection persists during session

## 20. Security Hardening Rules (Current & Recommended)

### 20.1 Currently Implemented
- Password hashing with bcrypt
- Session-based authentication with httpOnly cookies
- CORS with credential support
- Parameterized SQL queries
- Row-level locking for concurrent operations
- Security event logging
- JSON parsing error handling
- Duplicate detection on registration

### 20.2 Recommended (Not Yet Implemented)
- CSRF protection for state-changing operations
- Security headers (Helmet): CSP, HSTS, X-Frame-Options, X-Content-Type-Options
- Rate limiting on authentication endpoints
- Session regeneration on login (prevent fixation)
- Password complexity enforcement at registration (already in code, but should be backend-only)
- Cryptographic RNG for PIN generation (currently uses Math.random)
- TLS/HTTPS enforcement in production
- Account lockout after failed login attempts
- Password expiration policy
- Audit log rotation and retention policy
